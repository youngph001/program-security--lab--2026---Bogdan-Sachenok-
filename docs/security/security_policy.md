## 1. Purpose

Метою політики є встановлення обов'язкових правил безпечної розробки SecureScan, спрямованих на:

- захист вихідного коду самої системи та вихідного коду, який надходить на аналіз від користувачів;
- захист секретів, ключів, токенів і конфігурації;
- забезпечення контрольованого реагування на виявлені вразливості;
- запобігання ситуаціям, коли сама система (або її компонент-парсер) стає джерелом нових уразливостей.

Політика пов'язана з [`project_policy.md`](../policy/project_policy.md) (загальні правила розробки) та [`threat_model.md`](threat_model.md) (конкретні сценарії порушень за STRIDE).

## 2. Scope

Політика поширюється на:

- весь код у `src/` та `tests/`;
- конфігурацію CI/CD;
- сценарії розгортання (Docker, deployment-скрипти);
- документацію з безпеки в `docs/security/`;
- будь-які зовнішні залежності, додані через Composer.

Політика обов'язкова для всіх, хто створює або змінює артефакти проєкту: розробників, рев'юерів, ШІ-агентів.

**Поза межами політики:**

- безпека операційної системи хостів (відповідальність DevOps);
- фізична безпека обладнання;
- внутрішня реалізація сторонніх Git-хостингів (GitHub / GitLab);
- безпека сторонніх правил безпеки, якщо вони постачаються як зовнішній контент (відповідальність постачальника правил).

## 3. Roles and Responsibilities

| Роль | Відповідальність |
|---|---|
| Власник проєкту | Затверджує політику, дозволяє винятки, приймає залишковий ризик |
| Розробник | Дотримується вимог під час внесення змін |
| Рев'юер | Перевіряє зміни, що торкаються автентифікації, авторизації, криптографії, роботи з файлами |
| ШІ-агент | Виконує задачі в межах правил; не приймає самостійних рішень щодо послаблення вимог безпеки |

Затвердження винятків — виключно власник проєкту.

## 4. Security Principles

- **Least Privilege.** Кожен компонент має лише ті дозволи, які необхідні для його роботи.
- **Deny by Default.** Усе, що не дозволено явно — заборонено.
- **Secure by Default.** Стандартна конфігурація є безпечною без додаткових налаштувань.
- **Defense in Depth.** Один механізм захисту не є єдиним бар'єром.
- **Fail Securely.** Помилка захисного механізму не повинна призводити до компрометації системи.
- **No Secrets in Source Code.** Секрети (ключі, токени, паролі) не зберігаються в репозиторії, комітах, логах або артефактах збірки.
- **Explicit Trust Boundaries.** Межі довіри між компонентами явно визначені у [`threat_model.md`](threat_model.md).
- **Мінімізація даних.** Система зберігає лише ті дані, які необхідні для виконання функцій. Вихідний код користувача видаляється після сканування.
- **Sandboxing.** Аналізований код ніколи не виконується. Парсер працює в ізольованому середовищі з обмеженими правами.

## 5. Secure Development Environment

### 5.1. Доступ до репозиторію

- Лише через особисті облікові записи GitHub.
- Спільні акаунти заборонені.
- Обов'язкова двофакторна автентифікація (2FA) для всіх учасників.

### 5.2. Робота з Git

- Прямий push у `main` заборонений.
- Усі зміни — через Pull Request.
- Force-push у захищені гілки заборонений.
- Branch protection: обов'язковий review та обов'язковий CI перед merge.

### 5.3. Секрети

- Зберігаються у змінних оточення або у сховищі секретів (GitHub Secrets, Vault).
- У коді — лише читання з ENV.
- `.env` файли додані в `.gitignore`; у репозиторії лише `.env.example` без реальних значень.

### 5.4. Залежності

- Нові залежності додаються лише після перевірки: походження (офіційний пакет), ліцензія (сумісна), відсутність критичних CVE (`composer audit`).
- `composer.lock` завжди закомічений для відтворюваності збірок.

### 5.5. Інструменти

Обов'язкові перевірки:

- **PHPStan** (level max) — статичний аналіз.
- **Laravel Pint** — форматування коду.
- **PHP Deptrac** — контроль меж шарів.
- **PHPUnit** — тестування.

### 5.6. CI/CD

Кожен PR проходить CI з етапами:

1. Лінтер (Pint).
2. Статичний аналіз (PHPStan).
3. Контроль меж шарів (Deptrac).
4. Повний тест-сьют (PHPUnit).
5. Перевірка залежностей (`composer audit`).

Провал хоч однієї перевірки блокує merge.

### 5.7. ШІ-агенти

- Працюють лише в межах конкретної задачі.
- Не мають доступу до production-секретів.
- Використовують лише локальні або дозволені AI-сервіси без передачі чутливого коду назовні.

## 6. Software Protection

- **Захист коду.** Основний репозиторій — приватний під час розробки. Усі коміти підписані GPG (за можливості).
- **Branch protection.** Гілка `main` захищена: обов'язковий PR, обов'язковий CI, обов'язковий review для критичних змін.
- **Цілісність артефактів.** Релізні артефакти (Composer-пакет, Docker image) формуються лише через CI і підписуються.
- **Секрети.** Ніколи не потрапляють у репозиторій, логи, стектрейси, повідомлення про помилки.
- **Захист збірок.** Docker-образи збираються у CI, base image — офіційний і pinned за digest.
- **Мінімізація чутливих даних у логах.** У логах — лише UUID сканування, тип помилки, код винятку. Вихідний код і пейлоади вразливостей у логах не зберігаються.
- **Видалення даних.** Після завершення сканування завантажений архів / клонований репозиторій видаляються.

## 7. Secure Implementation

### 7.1. Валідація вхідних даних

- Усі зовнішні вхідні дані вважаються недовіреними.
- Валідація — на межі шару Presentation, до входу в Application.
- URL Git-репозиторію валідується: лише `https://`, лише whitelisted хостинги.
- Розмір архіву перевіряється **до** розпакування.
- Захист від zip-bomb: обмеження на кількість файлів та загальний розпакований розмір.

### 7.2. Автентифікація та авторизація

- Автентифікація — на рівні API (у майбутньому); поки що система працює як внутрішній інструмент.
- Авторизація перевіряється на серверному боці.
- Користувач має доступ лише до своїх сканувань.

### 7.3. Робота з файлами

- Файли зберігаються у тимчасовій директорії з обмеженими правами.
- Шляхи перевіряються: заборона `../`, абсолютних шляхів, симлінків.
- AST-парсер працює в sandbox без доступу до мережі.

### 7.4. Криптографія

- Самостійна реалізація криптографічних алгоритмів заборонена.
- Використовуються лише стандартні бібліотеки PHP (`sodium`, `openssl`) або визнані пакети.
- Паролі (у майбутньому) — лише через `password_hash` з `PASSWORD_ARGON2ID`.

### 7.5. Серіалізація та десеріалізація

- PHP-серіалізація (`unserialize`) недовірених даних заборонена.
- JSON — основний формат обміну.

### 7.6. Робота з БД

- Підготовлені вирази (prepared statements) — обов'язкові.
- Конкатенація SQL-рядків — заборонена.

### 7.7. Обробка помилок

- Користувачу — загальне повідомлення + код винятку (напр., `SS.SCAN.1`).
- Внутрішні деталі — лише в логах.
- Stacktrace ніколи не потрапляє у відповідь клієнту.

### 7.8. Логування

**Заборонено логувати:**

- вихідний код користувача;
- пейлоади вразливостей;
- секрети, токени, паролі;
- персональні дані.

**Дозволено логувати:**

- UUID сканування;
- тип помилки та код винятку;
- таймстемпи;
- технічні метрики.

### 7.9. Заборонені практики

- `eval()`, `exec()`, `shell_exec()`, `system()`, `passthru()` — заборонені.
- Виконання аналізованого коду — заборонене.
- `unserialize()` на недовірених даних — заборонене.

## 8. Security Verification

- **Code review.** Обов'язковий для змін у: автентифікації, авторизації, криптографії, роботі з файлами, парсингу.
- **Static analysis.** PHPStan (level max) на кожен PR.
- **Dependency scanning.** `composer audit` на кожен PR.
- **Unit-тести.** Обов'язкові негативні сценарії: невалідні вхідні дані, zip-bomb, шляхи з `../`, відсутність доступу до Git.
- **Security gate.** Наявність критичної відомої вразливості в залежності блокує merge.
- **Автоматизовані перевірки.** Лінтер + PHPStan + Deptrac + PHPUnit — обов'язкові в CI.

## 9. Vulnerability Management

- **Джерела.** `composer audit`, GitHub Security Advisories, повідомлення від користувачів, внутрішній review.
- **Реєстрація.** Кожна підтверджена вразливість — окремий GitHub Issue з мітками `security`, `severity:critical|high|medium|low`.
- **Класифікація.** За CVSS v3.1: Critical (9.0–10.0), High (7.0–8.9), Medium (4.0–6.9), Low (0.1–3.9).
- **Строки усунення:**
  - Critical — 24 години;
  - High — 7 днів;
  - Medium — 30 днів;
  - Low — 90 днів.
- **Перевірка виправлення.** Обов'язковий regression-тест на відтворення вразливості + підтвердження, що тест проходить після фіксу.
- **Root cause analysis.** Для Critical і High — обов'язковий аналіз причин та оновлення політики / моделі загроз, якщо прогалина системна.
- **Оновлення документів.** Якщо вразливість виникла через прогалину в політиці або моделі загроз — відповідні документи оновлюються.

## 10. Privacy Policy

Політика конфіденційності винесена в окремий документ: [`privacy_policy.md`](privacy_policy.md).

Коротко:

- Система обробляє вихідний код користувача та метадані сканувань.
- Вихідний код не зберігається після завершення сканування.
- Метадані сканувань зберігаються 90 днів, після чого видаляються.
- Персональні дані (email) — лише для автентифікації (у майбутньому).

## 11. Exceptions

- Відступ від вимог політики допускається лише після письмового обґрунтування, оцінки ризику та погодження власником проєкту.
- Кожен виняток має:
  - обґрунтування (чому неможливо дотриматись);
  - компенсуючі заходи (що зменшує ризик);
  - строк дії (не більше 90 днів);
  - власника ризику (хто приймає залишковий ризик).
- Після завершення строку — обов'язковий повторний перегляд.
- Винятки фіксуються в окремому реєстрі в Issues репозиторію з міткою `security-exception`.
