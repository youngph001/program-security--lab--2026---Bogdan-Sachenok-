## Scope

Модель охоплює:

- HTTP API (Presentation / EntryPoint);
- Application-шар (UseCases);
- Domain-шар (`Scan`, `Report`, `Rule`);
- Infrastructure-шар (Transport, Persistence, Parser);
- базу даних метаданих та результатів;
- чергу асинхронних сканувань;
- взаємодію із зовнішніми Git-хостингами.

**Поза межами моделі:**

- безпека операційної системи хостів (відповідальність DevOps);
- фізичний доступ до обладнання;
- внутрішня реалізація Git-хостингів (GitHub / GitLab);
- безпека сторонніх AI-сервісів (не використовуються).

## System Overview

SecureScan — система статичного аналізу вихідного коду на вразливості. Користувач надсилає код через HTTP API (архів або Git-URL). Система асинхронно обробляє його в ізольованому середовищі та формує звіт.

### Елементи DFD

| ID | DFD Type | Name |
| --- | --- | --- |
| E1 | External Interactor | Developer (User) |
| E2 | External Interactor | Git Hosting (GitHub / GitLab) |
| P1 | Process | HTTP API (Presentation) |
| P2 | Process | Application (UseCases / Orchestration) |
| P3 | Process | Domain Scanner (SAST engine) |
| P4 | Process | Parser (AST parser, sandbox) |
| D1 | Data Store | Database (scans, reports, vulnerabilities) |
| D2 | Data Store | Temporary File Storage (uploaded / cloned code) |
| D3 | Data Store | Queue (async scan jobs) |
| F1 | Data Flow | E1 User → P1 API (upload code / submit URL) |
| F2 | Data Flow | P1 API → D3 Queue (enqueue scan) |
| F3 | Data Flow | D3 Queue → P3 Domain Scanner (dequeue) |
| F4 | Data Flow | P3 Domain Scanner → P4 Parser (parse file) |
| F5 | Data Flow | P3 Domain Scanner → D1 Database (save results) |
| F6 | Data Flow | P1 API → E2 Git Hosting (clone repo) |
| F7 | Data Flow | P1 API → D2 Temp Storage (save uploaded archive) |
| TB1 | Trust Boundary | Client / API |
| TB2 | Trust Boundary | API / Internal processing |
| TB3 | Trust Boundary | SecureScan / External Git |

### Зв'язки

- `E1 User` взаємодіє з `P1 API` через `F1`.
- `F1` перетинає `TB1`.
- `P1 API` передає задачу в `D3 Queue` через `F2` (перетинає `TB2`).
- `D3 Queue` віддає задачу `P3 Domain Scanner` через `F3`.
- `P3 Domain Scanner` викликає `P4 Parser` через `F4`.
- `P3 Domain Scanner` зберігає результати в `D1 Database` через `F5`.
- `P1 API` клонує репозиторій з `E2 Git Hosting` через `F6` (перетинає `TB3`).
- `P1 API` зберігає архів у `D2 Temp Storage` через `F7`.

## STRIDE Analysis

### Відповідність STRIDE типам елементів

Позначення: **S** — Spoofing; **T** — Tampering; **R** — Repudiation; **I** — Information Disclosure; **D** — Denial of Service; **E** — Elevation of Privilege.

---

### E1. Developer (External Interactor)

| S | R |
|---|---|
| Зловмисник може видавати себе за легітимного користувача, використавши вкрадені токени доступу або сесію. | Користувач може заперечувати факт завантаження певного коду або запуску конкретного сканування. |

### E2. Git Hosting (External Interactor)

| S | R |
|---|---|
| Підміна Git-хостингу через MITM або DNS-спуфінг може призвести до клонування зловмисного репозиторію замість легітимного. | Git-хостинг може заперечувати факт передачі певного вмісту. |

---

### P1. HTTP API (Process)

| S | T | R | I | D | E |
|---|---|---|---|---|---|
| Підміна клієнта через відсутність або слабкість автентифікації. | Зміна параметрів запиту (URL, розмір, тип архіву) для обходу валідації. | Відсутність аудит-логу для критичних операцій унеможливлює доведення факту запиту. | Помилка в авторизації може дозволити перегляд чужих сканувань. | Flood запитами (DoS) виснажує ресурси API. | Помилка авторизації → доступ до чужого сканування або операцій. |

### P2. Application (Process)

| S | T | R | I | D | E |
|---|---|---|---|---|---|
| Виконання юзкейсу від імені іншого користувача за відсутності перевірки контексту. | Модифікація вхідних DTO до їх обробки юзкейсом. | Неповний аудит оркестрації ускладнює розслідування. | Логіка оркестрації може розкрити внутрішні ідентифікатори при помилках. | Довготривалі юзкейси блокують воркер. | Недостатня перевірка дозволів перед викликом Domain. |

### P3. Domain Scanner (Process)

| S | T | R | I | D | E |
|---|---|---|---|---|---|
| Спуфінг внутрішнього виклику від імені іншого юзкейсу (внутрішньосервісна підміна). | Підміна правил або результатів парсингу в пам'яті. | Відсутність логів у Domain ускладнює доведення виконання операцій. | Помилки у логіці можуть розкрити вміст чужого коду через звіт. | Складна вразливість у коді може призвести до нескінченного циклу під час аналізу (ReDoS). | Помилка в політиці переходів статусу → можлива небажана зміна статусу чужого сканування. |

### P4. Parser (Process)

| S | T | R | I | D | E |
|---|---|---|---|---|---|
| — (внутрішній ізольований процес). | Обробка спеціально сконструйованого файлу може призвести до непередбачуваної поведінки парсера. | — | Парсер має доступ до вихідного коду — у разі компрометації можливий витік. | ReDoS або zip-bomb у файлі може виснажити ресурси парсера. | Вихід за межі sandbox через вразливість у парсері (наприклад, RCE). |

---

### D1. Database (Data Store)

| T | I | D |
|---|---|---|
| Несанкціонована зміна результатів сканування або метаданих. | Несанкціонований доступ може призвести до розкриття результатів та зв'язків між скануваннями. | Блокування або перевантаження БД робить систему недоступною. |

### D2. Temporary File Storage (Data Store)

| T | I | D |
|---|---|---|
| Підміна файлу користувача після завантаження до початку сканування. | Вихідний код користувача є чутливим; несанкціонований доступ = витік комерційної таємниці. | Заповнення диска через великі архіви або zip-bomb. |

### D3. Queue (Data Store)

| T | I | D |
|---|---|---|
| Підміна задачі в черзі → виконання чужого сканування під виглядом свого. | Перехоплення задачі може розкрити метадані (UUID, тип джерела). | Переповнення черги → сканування не виконуються. |

---

### F1. User → API (Data Flow)

| T | I | D |
|---|---|---|
| Запит може бути змінений до його обробки сервером. | Дані запиту (код, URL, токени) можуть бути перехоплені при відсутності TLS. | Потік може бути заблокований або перевантажений. |

### F2. API → Queue (Data Flow)

| T | I | D |
|---|---|---|
| Зміна задачі до її потрапляння в чергу. | Метадані задачі можуть бути розкриті при відсутності шифрування. | Черга може бути переповнена. |

### F3. Queue → Scanner (Data Flow)

| T | I | D |
|---|---|---|
| Підміна задачі у момент її вибору воркером. | Розкриття деталей задачі. | Воркер може не отримати задачу. |

### F4. Scanner → Parser (Data Flow)

| T | I | D |
|---|---|---|
| Підміна файлу перед парсингом. | Розкриття вмісту файлу за межами sandbox. | Файл занадто великий → парсер блокується. |

### F5. Scanner → Database (Data Flow)

| T | I | D |
|---|---|---|
| Модифікація запиту запису результатів. | Результати можуть бути розкриті при відсутності TLS до БД. | Запис може бути заблокований. |

### F6. API → Git Hosting (Data Flow)

| T | I | D |
|---|---|---|
| Підміна відповіді Git-хостингу → клонування зловмисного репозиторію. | Розкриття токену доступу до приватних репозиторіїв. | Git-хостинг недоступний → сканування не запускається. |

### F7. API → Temp Storage (Data Flow)

| T | I | D |
|---|---|---|
| Підміна архіву після запису. | Доступ до тимчасового файлу третіми процесами. | Заповнення диска. |

## Пріоритезація загроз

| # | Загроза | STRIDE | Severity | Компенсуючі заходи |
|---|---|---|---|---|
| 1 | Витік вихідного коду користувача | I | Critical | Шифрування, видалення після сканування, обмежений доступ |
| 2 | RCE через вразливість у парсері | E | Critical | Sandbox, обмежені права, обмеження розміру |
| 3 | ReDoS / zip-bomb | D | High | Обмеження розміру та кількості файлів, таймаути |
| 4 | SQL-ін'єкції | T | High | Prepared statements, заборони конкатенації SQL |
| 5 | Підміна Git-хостингу | S | High | Whitelist хостингів, пінning TLS-сертифікатів |
| 6 | Помилка авторизації до чужих сканувань | E | High | Перевірка власника на серверному боці |
| 7 | DoS на API | D | Medium | Rate limiting, ліміти розміру запитів |
| 8 | Розкриття метаданих у логах | I | Medium | Заборона чутливих полів у логах |
| 9 | Заперечення факту дії | R | Low | Аудит-логи критичних операцій |

## Висновки

- Найбільш критичними є загрози витоку вихідного коду користувача та компрометації sandbox парсера.
- Основні компенсуючі заходи: ізоляція (sandbox), шифрування (TLS), мінімізація даних (видалення коду після сканування), явні межі довіри.
- Загрози, пов'язані з користувацькою автентифікацією (S, E), стануть актуальнішими при реалізації багатокористувацького доступу в майбутньому.
- Модель загроз має переглядатися після суттєвих змін архітектури (наприклад, додавання нових типів джерел аналізу або підтримки нових мов).
