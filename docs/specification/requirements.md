# Requirements — SecureScan (Program Security Lab 2026)

> Специфікація вимог до системи. Складена згідно з ISO/IEC/IEEE 29148:2018.
> Кожна вимога є атомарною, однозначною та перевірюваною.

## 1. Функціональні вимоги (FR)

| ID | Вимога | Критерій перевірки |
|---|---|---|
| FR-1 | Система приймає на вхід архів з вихідним кодом (.zip, .tar.gz) | Після завантаження архіву система повертає `scanId` |
| FR-2 | Система приймає на вхід посилання на публічний Git-репозиторій | Після вказання URL система клонує репозиторій і повертає `scanId` |
| FR-3 | Система запускає статичний аналіз (SAST) завантаженого коду | Після завершення сканування статус змінюється з `PENDING` на `COMPLETED` |
| FR-4 | Система виявляє SQL-ін'єкції в коді | На тестовому файлі з SQL-ін'єкцією система повертає вразливість типу `SQL_INJECTION` |
| FR-5 | Система виявляє XSS-вразливості | На тестовому файлі з XSS система повертає вразливість типу `XSS` |
| FR-6 | Система виявляє витік чутливих даних (API-ключі, паролі) | На файлі з hardcoded ключем система повертає вразливість типу `SECRET_LEAK` |
| FR-7 | Система класифікує кожну вразливість за рівнем критичності | Кожна вразливість має рівень: `LOW`, `MEDIUM`, `HIGH`, `CRITICAL` |
| FR-8 | Система формує звіт у форматі JSON | Після сканування доступний файл `report.json` із валідною схемою |
| FR-9 | Система формує звіт у форматі HTML | Після сканування доступний файл `report.html`, що відкривається в браузері |
| FR-10 | Система зберігає історію сканувань | Запит `ListScansAQ` повертає всі попередні сканування проєкту |
| FR-11 | Система дозволяє отримати результати конкретного сканування | Запит `GetScanAQ` за `scanId` повертає деталі сканування |
| FR-12 | Система скасовує сканування, що виконується | Після `CancelScanAC` статус змінюється на `CANCELLED` |

## 2. Нефункціональні вимоги (NFR)

| ID | Вимога | Критерій перевірки |
|---|---|---|
| NFR-1 | Час сканування проєкту до 1000 файлів ≤ 60 секунд | Замір на еталонному проєкті |
| NFR-2 | Час відповіді на `GetScanAQ` ≤ 200 мс на p95 | Замір на 1000 запитах |
| NFR-3 | Система підтримує одночасне сканування мінімум 10 проєктів | Навантажувальний тест |
| NFR-4 | Усі винятки системи реалізують базову абстракцію `ASecureScanException` | Статична перевірка коду |
| NFR-5 | Покриття Domain-шару юніт-тестами ≥ 90% | Звіт PHPUnit (clover) |
| NFR-6 | Покриття Application-шару юніт-тестами ≥ 80% | Звіт PHPUnit (clover) |
| NFR-7 | Жодних реальних мережевих викликів під час тестів | Перевірка CI (усі зовнішні залежності — моки) |
| NFR-8 | Система не зберігає вихідний код користувача після сканування | Перевірка: після завершення сканування тимчасові файли видалені |
| NFR-9 | Усі логи сканування не містять чутливих даних із проаналізованого коду | Ручна перевірка логів |
| NFR-10 | Система підтримує PHP 8.3+ | Перевірка `composer.json` та CI |
| NFR-11 | Час запуску системи (cold start) ≤ 2 секунди | Замір на CI-середовищі |
| NFR-12 | Звіт JSON відповідає схемі `scan-report.schema.json` | Валідація схеми в тестах |
## 3. Обмеження (Constraints)
| ID | Обмеження |
|---|---|
| C-1 | Система не виконує аналізований код (тільки статичний аналіз) |
| C-2 | Система не має доступу до приватних репозиторіїв без токена |
| C-3 | Розмір архіву для завантаження ≤ 100 МБ |
| C-4 | Підтримувані мови аналізу: PHP, JavaScript |
| C-5 | Система не надає API для автоматичного виправлення коду |
## 4. Припущення (Assumptions)
- Користувач має права на код, який завантажує на аналіз.
- Мережа між клієнтом та системою — стабільна.
- Git-репозиторії, що передаються на аналіз, доступні публічно або за токеном.
