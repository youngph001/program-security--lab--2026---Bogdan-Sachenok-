# Політика документації — SecureScan

> Актуальна база знань поруч із кодом. Документація — повноцінний деліверабл; застаріла чи відсутня документація вважається дефектом.

## Принципи

- Документація змінюється разом із кодом, а не після нього.
- Зміни у вимогах, структурі або правилах розробки супроводжуються змінами в документації.
- Застаріла документація = дефект.
- Жодних документів «просто так» — кожен файл має практичне призначення.

## Структура

```text
docs/
├── README.md                          # точка входу
├── contexts_registry.md               # реєстр усіх BC
├── changelog.md                       # журнал змін документації
├── specification/
│   ├── scope.md                       # межі проєкту
│   ├── requirements.md                # вимоги (FR / NFR)
│   └── architecture.md                # архітектурний опис
├── policy/
│   ├── project_policy.md              # політика проєкту
│   └── project_documentation_policy.md # цей файл
├── guide/
│   └── getting_started.md             # як почати роботу
└── internal_spec/
    └── [Назва]/                       # одна директорія на BC
        ├── business_logic.md          # стабільний концептуальний зміст
        ├── changelog.md               # append-only журнал змін
        └── tech_notes.md              # техборг, edge cases
```

## Обов'язки

Кожен, хто змінює модуль:

1. Додає запис у `docs/internal_spec/[Модуль]/changelog.md`.
2. Звіряє та за потреби оновлює `docs/internal_spec/[Модуль]/business_logic.md`.
3. Фіксує в `docs/internal_spec/[Модуль]/tech_notes.md` новий техборг / особливості / закриті проблеми.
4. Додає запис у загальний `docs/changelog.md`, якщо зміна суттєва.

Файли документації створює той, хто створює модуль.

## Формат запису в changelog

```markdown
## [YYYY-MM-DD] [TICKET-XXX] Назва зміни
- зміна 1
- зміна 2
```

Нові записи — на початок файлу. Файл строго append-only.

## Стиль

- Максимально лаконічно, списками, але вичерпно.
- Без незначущих деталей, але й без пропуску важливого.
- Приклади — конкретні, а не абстрактні.
- Українською мовою (крім технічних термінів і назв).

## Узгодженість документів

Документи мають бути взаємно узгодженими:

- Вимоги (`requirements.md`) не суперечать бізнес-логіці (`business_logic.md`).
- Архітектура (`architecture.md`) дозволяє реалізувати вимоги.
- Політики (`policy/`) відповідають фактично обраним технологіям та структурі проєкту.
