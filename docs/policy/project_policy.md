> Ця політика визначає обов'язкові вимоги до коду та архітектури `SecureScan` — системи автоматизованого статичного аналізу вихідного коду на наявність вразливостей безпеки. Ключові вимоги: строго типізоване ООП за SOLID, чистий код, шарова архітектура з примусовими межами між шарами та тестове покриття.
>
> Проєкт свідомо НЕ робить: динамічний аналіз (DAST), автоматичне виправлення коду, управління користувачами, написання власних правил безпеки.

## Правила зміни політики

- **Жодних змін мимохід** — політика не змінюється як побічний ефект іншої задачі; зміни вносяться лише окремою задачею на оновлення політики.
- **Обов'язковий апрув** — будь-яка зміна попередньо погоджується з власником проекту.
- **Окремий комміт + інкремент версії** — зміни політики йдуть окремим git-коммітом з префіксом `[POLICY]` у повідомленні та підняттям версії документа.

## Фундаментальні принципи

- **Розділення шарів.** Змішування інфраструктурного (транспортного) шару, шару бізнес-логіки та фреймворк-шару строго заборонене. Кожен шар ізольований і не протікає в інші.
- **DDD для бізнес-логіки.** Бізнес-логіка реалізується в парадигмі DDD настільки, наскільки це доцільно.
- **Чужа логіка поза проектом.** Проект не містить бізнес-логіки систем, які його використовують / з якими інтегрується — вона залишається на їхньому боці.
- **Опційність фреймворку.** Фреймворк-орієнтовані механізми (якщо є) — опційні; без фреймворку ядро проекту залишається повністю функціональним. Фреймворк не проникає в Domain/Application.
- **Строго типізоване ООП, SOLID, чистий код.**
- **Непорушність політики.** Жодні обставини не є легітимною підставою для порушення цієї політики.

## Архітектура та структура

Проект розділений на ізольовані шари; виклики йдуть лише зверху вниз — нижні шари не залежать від верхніх.

Глобальна структура `src/`:

```text
src/
├── EntryPoint.php      # точка входу
├── Infrastructure/     # транспорт, персистенс, зовнішні сервіси
├── Domain/             # бізнес-логіка: BC Scan, Report, Rule + SharedKernel
├── Application/        # оркестрація: UseCase, Command, Query, Dto
└── Framework/          # опційний фреймворк-шар
```

Напрямок залежностей:

```text
EntryPoint/Presentation + Facade → Application → Domain ←[контракти]→ Infrastructure
<Framework> → (опційна обгортка; від неї ніхто не залежить)
```

### Domain

Domain розділений на **bounded contexts** — `Scan`, `Report`, `Rule` та `SharedKernel`.

Скелет БК:

```text
Domain/[BoundedContext]/
├── Entity/
├── ValueObject/
├── Enum/
├── Exception/
├── OutsourceContract/   # контракти назовні, до Infrastructure — обов'язково
├── Service/
├── Policy/              # опційно
├── Event/               # опційно
└── Contract/            # внутрішні контракти БК — опційно
```

**Гомогенні директорії.** Директорія містить елементи одного роду. Базові абстракції — `Abstracts/`, реєстри — `Registry/`, внутрішні контракти — `Contract/`.

**SharedKernel** — спільне ядро для всіх БК:

```text
Domain/SharedKernel/
├── Abstracts/      # базові абстракції (AValueObject, AEntity, AEntityUuidVO, ASecureScanException)
├── Contract/       # фундаментальні інтерфейси (IValueObject, IEntity, ISecureScanException)
├── ValueObject/    # спільні VO
├── Enum/           # спільні енуми
└── Exception/      # CoreExceptionRegistry, ACoreException
```

До SharedKernel потрапляє лише справді крос-БК-шне. Додавання нового елемента в SharedKernel потребує попереднього апруву власника.

### Infrastructure

```text
Infrastructure/
├── Transport/     # HTTP-клієнт для Git, HTTP API
├── Persistence/   # БД: ScanModel, ReportModel, VulnerabilityModel
├── Parser/        # AST-парсер PHP/JS
└── Exception/     # інфраструктурні винятки
```

### Application

Тонкий шар оркестрації (юзкейси), без бізнес-правил; реалізує CQRS. Групується по БК.

```text
Application/[BoundedContext]/
├── UseCase/       # StartScanUC, GetScanUC, ListScansUC
├── Command/       # StartScanAC, CancelScanAC
├── Query/         # GetScanAQ, ListScansAQ
├── Dto/           # ScanDTO, VulnerabilityDTO
└── Exception/     # винятки рівня Application
```

### Точка входу / Presentation

Верхній шар. Presentation (HTTP-контролери, консольні команди) лише приймає ввід, викликає юзкейси та формує відповідь.

### Фреймворк-шар

Опційний шар — обгортка, що вбудовує проект у фреймворк. Допускає довільну структуру. Від нього ніхто не залежить.

## Політика доменних івентів

Кожен Domain Event (DE) складається з: **UUID** івента, **UUID ентіті**-джерела, **таймстемпа**, **пейлоада** (окремий DED-об'єкт), **імені івента** та **версії** схеми.

- Конкретний DE успадковує `ADomainEvent` і декларує `getEventName()` та `getEventDataClass()`. Рекомендована статична фабрика `::withData(...)`.
- **DED** — окремий `final readonly` клас пейлоада; відповідає за власну серіалізацію (`toArray()` / `loadFromArray()`).
- **Реєстр івентів** — `Enum` у Domain-шарі БК; значення кейсів формату `<БК>.<Івент>`.
- Ентіті, що публікує івенти, використовує чергу івентів (trait із SharedKernel): `triggerEvent()`, `pullEvents()`.
- **Життєвий цикл:** ентіті тригерить івент у внутрішню чергу → UseCase зберігає ентіті → Infrastructure після збереження робить `pullEvents()` і диспатчить → лісенери ініціюють команди вниз по вертикалі.

## Політика неймінгу

**Загальне:**

- Класи, інтерфейси, абстракти, трейти, енуми — `PascalCase`.
- Методи, змінні, параметри — `camelCase`; константи — `UPPER_SNAKE_CASE`.
- Файл = ім'я класу; директорії — `PascalCase`.

**Префікси / суфікси:**

| Тип | Конвенція | Приклад |
|---|---|---|
| Інтерфейс | префікс `I` | `IScanRepository` |
| Абстрактний клас | префікс `A` | `AValueObject`, `AEntityId` |
| Entity / Aggregate Root | без суфікса | `Scan` |
| Value Object | суфікс `VO` | `ScanStatusVO` |
| Enum | без суфікса | `ScanStatus` |
| Доменний сервіс | суфікс `Service` | `ScanFactoryService` |
| Доменна політика | суфікс `DPolicy` | `StartPendingScanDPolicy` |
| Domain Event | суфікс `DE` | `ScanStartedDE` |
| Use Case | суфікс `UC` | `StartScanUC` |
| Application Command | суфікс `AC` | `StartScanAC` |
| Application Query | суфікс `AQ` | `GetScanAQ` |
| DTO | суфікс `DTO` | `ScanDTO` |
| Виняток | суфікс `Exception` | `ScanNotFoundException` |
| Реєстр винятків | суфікс `ExceptionRegistry` | `ScanExceptionRegistry` |
| База винятків | префікс `A` + суфікс `Exception` | `AScanException` |
| Service Provider фреймворку | суфікс `ServiceProvider` | `SecureScanServiceProvider` |

**Імпорти:** зовнішні класи — через `use` вгорі файлу; у PHPDoc — ті самі короткі імена.

**Директорії:** `PascalCase`, назва відповідає типу елемента.

## Політика анотацій (PHPDoc)

Анотації обов'язкові для **кожного** метода та властивості класу. Відсутня анотація — помилка.

**Докблок метода містить:**

- `@param` — для кожного параметра з точним типом.
- `@return` — тип повернення (включно з `@return void`).
- `@throws` — для кожного винятку.
- Лаконічний опис призначення метода.

**Докблок класу містить:**

- `@package` — пакет/неймспейс.
- Лаконічний опис призначення.

**Докблок властивості містить:**

- `@var` — точний тип.
- Лаконічний опис.

**Для `Entity` / `Aggregate Root` / `Value Object`** докблок класу додатково містить список ключових **інваріантів**.

## Політика винятків

Усі винятки проекту реалізують базову абстракцію `ASecureScanException` із `SharedKernel` (яка реалізує контракт `ISecureScanException`). Сторонні та системні винятки мають бути обгорнуті у відповідний внутрішній виняток.

### Структура коду винятку

Кожен виняток ідентифікується ієрархічним кодом:

```text
<ПРЕФІКС>.<Сегмент>.<код>
```

- **`<ПРЕФІКС>`** — `SS` (SecureScan), єдине джерело — `SharedKernel`.
- **`<Сегмент>`** — `SCAN`, `REPT`, `RULE`, `INF`, `CORE`.
- **`<код>`** — числовий код, унікальний у межах свого реєстру.

Приклади: `SS.SCAN.1`, `SS.REPT.4`, `SS.INF.2`, `SS.CORE.1`.

Коди **іммутабельні після призначення**. При видаленні винятку кейс реєстру не видаляється, а помічається `#[Deprecated]`:

```php
#[Deprecated]
case UserEmailFormatInvalid = 1;
```

### Реєстри винятків

- **Реєстр БК** — один на BC; живе в `Domain/[Bc]/Exception/Registry/`. Сегмент — `SCAN`, `REPT`, `RULE`.
- **Реєстр інфраструктури** — один на Infrastructure; живе в `Infrastructure/Exception/Registry/`. Сегмент — `INF`.
- **CoreExceptionRegistry** — живе в `SharedKernel`. Сегмент — `CORE`.

Кожен реєстр — це `Enum`, що реалізує `IExceptionCodeRegistry`.

## NULL-less політика

Рекомендується мінімізувати фізичний `null` у бізнес-логіці та типізувати відсутність явно (null-object / reference-патерн). Це рекомендація, а не жорстка заборона.

## Політика тестування

### Інструменти

Основа — **PHPUnit**. Зовнішні залежності замінюються моками; **реальних мережевих викликів у тестах немає**. Тести не завантажують DI-контейнер фреймворку.

### Структура тестів

Директорія `tests/` віддзеркалює структуру `src/` — по шарах та БК.

### Пріоритет юніт-тестів

Юніт-тести пріоритетні всюди, де можливо. Кожен тест покриває і коректні, і свідомо невалідні сценарії.

### Покриття по шарах

- **Domain:** лише юніт; максимальне покриття (≥ 90%).
- **Application:** лише юніт; сценарії UseCase для різних Command / Query (≥ 80%).
- **Infrastructure:** юніт, де можливо; інтеграційні — проти замоканого транспорту.

### Групування тестів

```php
#[Group('domain')]
#[Group('scan.domain')]
#[Group('scan.domain.entity')]
final class ScanTest extends TestCase { ... }
```

## Політика документації розробки

Актуальна база знань поруч із кодом. Документація — повноцінний деліверабл.

### Структура

```text
docs/
├── contexts_registry.md
├── changelog.md
└── internal_spec/
    └── [Назва]/           # одна директорія на BC
        ├── business_logic.md
        ├── changelog.md
        └── tech_notes.md
```

- **Реєстр** — повний перелік BC.
- **`business_logic.md`** — стабільний концептуальний зміст модуля.
- **`changelog.md`** — append-only журнал змін.
- **`tech_notes.md`** — техборг, відомі проблеми, edge cases.

### Обов'язки

Кожен, хто змінює модуль: додає запис у `changelog.md`; оновлює `business_logic.md`; фіксує в `tech_notes.md` нові особливості.

### Стиль

Максимально лаконічно, списками, але вичерпно.
